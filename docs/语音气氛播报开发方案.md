# AcePoint 语音气氛播报开发方案

日期：2026-10-15。状态：首版已实现并完成Windows自动化及播放验证；树莓派／球馆验收待进行。本文保留原始设计基线，实际使用及实现差异见[使用说明](语音播报使用说明.md)。

## 1. 产品目标与范围

面向熟人羽毛球娱乐局，采用“热血电竞播报 + 朋友互损”的本地语音，在连得分、追分、关键比分和获胜时活跃气氛。台词围绕球技和比赛局势，不播队名。

用户已确定：熟人场景、接受当前讨论方向、先形成开发方案。播报频率尚未明确选择，本文采用建议默认值 **balanced（热闹一点）**，作为可调初始方案；台词均为待试听草案。

首版交付包含：

- 同一方连续得分的三／五／七连击，以及终结对手连得分。
- 落后追平、反超、破蛋、20平、29平、赛点、正常／逆转／大优势获胜。
- 普通得分偶尔插话，支持关键时刻模式和仅音效模式。
- 本机离线音频播放，网页静音、音量、频率和台词风格控制。
- 撤销、清零、重复事件、音频故障下的正确行为。

不在首版范围：在线生成语音、识别球员姓名、个性化声音克隆、自动判断真实回合、三局两胜、换边跟踪、跨重启恢复比赛。所有事件依据系统确认的得分；漏记或误记需要沿用现有方式纠正。

## 2. 当前代码与接入原则

| 现有位置 | 已有行为 | 计划改动 |
|---|---|---|
| `state.py / ScoreBoard` | 唯一比分来源；`apply()` 修改比分；`set_score()` 直接设置 | 保持现有返回值和比分语义，增加原子产生结构化变更的入口 |
| `engine.py / _tick_side()` | 手势直接调用 `board.apply()` | 经统一计分入口转交播报服务 |
| `engine.py / _drain_manual()` | 网页动作排队后调用 `board.apply()` | 与手势共用入口，避免漏播或规则不一致 |
| `rules.py` | `winner_of()`、`match_points()`，支持21分制及30分封顶 | 复用判定；语音层不另写胜负规则 |
| `displays/web.py` | Flask动作接口、SSE推送遥测 | 增加音频控制回调及状态字段 |
| `config.py` | 冻结 dataclass + TOML 配置 | 增加 `AudioConfig` 和校验 |
| `cli.py` | 自检、运行、硬件测试入口 | 计划增加音频自检和无摄像头试听入口 |

不能根据网页每次刷新、SSE重连、`last_event` 文本或 `flash_seq` 播放：这些不是可靠的得分事件。当前零分减分也会增加 `version`，必须结合动作及前后比分判断真实变化。

## 3. 事件与台词规则

以下默认阈值均通过配置调整。一分可产生多个候选事件，最终最多播放一个完整片段；片段包含短音效和语音，不再叠加另一条得分提示音。

| 事件ID | 精确定义与限次 | 示例台词 | 优先级 |
|---|---|---|---:|
| `win_comeback` | 有效加分使 `winner` 从无变为有，获胜方本局曾落后至少5分 | “逆风翻盘！刚才谁笑最大声？” | 100 |
| `win_dominant` | 获胜，且最终净胜至少10分；不满足逆转获胜 | “比赛结束！友情是否结束，另行通知！” | 100 |
| `win_normal` | 其余获胜 | “拿下！可以发群里了！” | 100 |
| `decider` | 有效加分首次形成29:29 | “最后一球！赢了吹一年！” | 90 |
| `deuce` | 有效加分首次形成20:20 | “加班！谁也别想准点下班！” | 85 |
| `match_point` | 得分方新进入 `match_points`，每方每局最多播一次 | “赛点！手别抖，嘴先闭上！” | 80 |
| `comeback_lead` | 曾落后至少5分后，从平分变为领先；每方每局一次 | “反超！让你先跑，你还当真了？” | 75 |
| `comeback_tie` | 曾落后至少5分后，从落后变为平分；每方每局一次 | “追平！刚才只是没开机！” | 70 |
| `streak_7` | 同一方连续有效得分恰好达到7分 | “超神！今天这场你买单！” | 65 |
| `streak_5` | 连续有效得分恰好达到5分 | “五连击！对面开始研究球拍了！” | 60 |
| `streak_3` | 连续有效得分恰好达到3分 | “三连击！你小子偷偷练了？” | 55 |
| `shutdown` | 本次得分前，对手连续得分至少3分 | “终结！装完了吧，该我了！” | 50 |
| `icebreaker` | 得分前本方0分、对方至少5分，本次本方变为1分；每方每局一次 | “破蛋！这不得庆祝一下？” | 52 |
| `banter` | balanced模式下，距离上次实际语音已有随机3～5个有效加分，且无更高候选 | “这球可以！再来一个！” | 10 |
| `point` | 没有语音候选时的短提示音，可关闭 | 不含语音，约0.15秒 | 0 |

规则补充：

- 连得分按有效加分序列统计，不按时间、手势保持时间或识别冷却统计；换得分方重新从1开始。到8分不再喊七连击，下一段连得分可重新触发3／5／7。
- 历史最大落后分差按每次有效比分计算。获胜分类固定按“逆转 > 大优势 > 普通”选择，不能连播三种获胜。
- `icebreaker` 与 `shutdown` 同时发生时优先破蛋。候选表中其余并列按固定事件ID顺序，保证结果可测试。
- 20平、29平的专用台词仅在 `target=21, win_by=2, cap=30` 时启用。自定义赛制仍使用现有赛点／获胜结果；`game.enabled=false` 时关闭所有赛制类事件，保留连得分等通用事件。
- 普通插话仅在条件满足的当前加分点尝试，不定时自言自语，不在停球、暂停时补播。
- 低优先级事件被更高事件覆盖后直接丢弃，不在下一分补播。
- 风格：`friends`（互损，默认）、`clean`（文明）；频率：`balanced`（默认）、`key_only`（关闭普通插话和普通得分音）、`effects_only`（沿用关键事件时机，只播放短音效）。静音是独立开关。

## 4. 得分历史、减分与防刷播

### 4.1 结构化比分变更

计划定义不可变 `ScoreChange`：`game_id`、`event_id`、动作、半场、来源、前后 `Snapshot`、单调时钟时间、是否真实改变比分。

在 `ScoreBoard` 的锁内构造前后状态。新增 `apply_with_change()`／`set_score_with_change()` 返回变更；原 `apply()`／`set_score()` 保留返回 `Snapshot` 的兼容包装。引擎统一通过新入口处理业务变更，直接设置比分也必须发出基线重建通知。`event_id` 单调递增，清零更新 `game_id`。

真正加分且比分发生变化才产生得分候选。零分减分和赛后被忽略的加分不触发音效、不改变连得分。有效清零即使原比分为0:0也视为开启新局。

### 4.2 与现有减分语义兼容

当前 `DECREMENT` 是指定半场减1，不是“撤回全局最后一个回合”。首版保留这个行为：

1. 在本局有效加分列表中，移除该半场最近的一条加分记录。
2. 按剩余记录原顺序重新计算连得分、各方最大落后分差、追平及反超资格。回放只恢复统计，不产生声音。
3. 如果移除的是全局最后一分，可以准确恢复到该分之前的统计；移除较早的一分则是修正后的有效得分序列，不宣称还原真实比赛过程。
4. `set_score()` 不包含回合顺序信息：清除历史，建立新的比分基线，历史连得分为0，追分统计从此刻开始，不根据比分猜测过去连得分。后续减分若无可移除记录，同样以修正后比分建立新基线。
5. 修正后若出现获胜方变化，也不播庆祝；只有有效加分造成的“无赢家 → 有赢家”转换才播获胜。

事件历史仅内存保存；正常21分制一局最多59个有效加分，重算成本很小。对关闭赛制的无限计分模式设置历史上限，超过上限建立新基线并清除依赖更早历史的资格，日志注明，不无限增长内存。

### 4.3 已经播放的声音与撤销分开处理

- 减分／直接设置比分：撤销待播事件，并停止当前播报，更新统计；不补播历史事件。
- 清零：清空待播、停止当前声音、清除旧局历史和去重记录；新局不自动喊开场，避免刷屏式重置。
- 比分统计可回滚，已经发生的播放记录不可回滚。实际开始播放时记录 `(game_id, event_type, side, left, right)`。
- 同一播放键在30秒内不再播，避免反复减分再加分刷同一句；普通得分音也受同键约束。每局限次事件另记录已播集合，撤销不解除限次。
- 获胜不设“每局永久只能一次”：撤销后再次合法获胜允许播报，但仍受上述30秒同键抑制；获胜方不同则是不同键。
- 队列内按 `event_id` 去重；被覆盖、静音或过期而未开始播放的候选，不写入已播记录。

## 5. 播放节奏与线程模型

流程：有效计分 → 同步更新轻量历史 → 生成候选／选最高优先级 → 投递有界播放器 → 延迟复核 → 本机扬声器。

计分与识别主循环不等待音频解码、声卡初始化或播放结束。候选处理采用单调时钟；音频工作线程独占播放后端。

建议初始参数：

| 参数 | 默认 | 行为 |
|---|---:|---|
| 触发延迟 | 0.4秒 | 给快速网页纠错留出撤回机会；不保证能等到受5秒冷却影响的手势撤销 |
| 两次普通语音起播最小间隔 | 6秒 | 限制普通插话、追分和连击；不满足就丢弃 |
| 关键事件 | 优先级≥80 | 可越过6秒间隔；仍受限次、去重和有效性检查 |
| 待播容量 | 1条 | 当前播放之外最多保留一条最高优先级待播，新同级替换旧同级 |
| 普通候选有效期 | 2秒 | 过期直接丢弃，不追着比赛补播 |
| 获胜候选有效期 | 5秒 | 撤销／新局立即失效，不受普通候选有效期影响 |
| 抢占淡出 | 80毫秒 | 关键事件可打断低优先级播报，淡出后启动新声音 |
| 普通／获胜片段最长 | 2.5／4秒 | 以实际录音时长验收；过长台词重写，不靠加速念完 |

新有效得分清除旧待播候选，仅保留当前分选出的候选；已起播普通片段可结束，获胜／关键事件按优先级抢占。同级关键事件以新分为准替换；所有播放前再次检查当前局、事件有效性及静音状态。

静音立即停止并清队列；取消静音后仅响应未来事件。音量为0等同不播放但保持设置。风格／频率切换清理待播，下一事件使用新设置。音频线程故障、缺声卡或缺文件只降级音频，不退出计分，不重试刷日志。

## 6. 播放技术与音频素材

拟采用可选依赖 `pygame` 的 `pygame.mixer`：仅初始化混音模块，使用单一显式 Channel 播放、停止、设置音量和淡出，不打开游戏窗口。依赖懒加载；`audio.enabled=false` 或 `backend="null"` 不导入 pygame。

官方接口依据：[pygame.mixer 文档](https://www.pygame.org/docs/ref/mixer.html)。Windows及树莓派的实际安装、声卡选择、无桌面 systemd 运行需要在第一阶段验证；此处是拟定方案，不代表已完成兼容测试。

- `NullPlayer`：记录事件供单元测试和硬件无关模拟。
- `PygamePlayer`：工作线程初始化和关闭，少量常用片段预载，整体音频缓存目标不超过16MB。
- 声音先离线录制或合成，运行时只播文件；使用自己的台词和音效素材，做电竞节奏，不依赖LOL原版录音。
- 首版每个语音事件至少3条，普通插话至少5条；先交付friends完整包，clean可先提供每事件1条，效果模式每种事件配短音效。独立随机数源用于选句，避免影响计分；同事件有多个文件时不连续选同一句。
- 建议统一PCM WAV、44.1kHz、16bit、单声道；响度统一，峰值留余量，避免某句突然爆响。短音效与语音预混为一个片段，控制总时长。
- 项目 `audio/friends/`、`audio/clean/`、`audio/effects/` 放可直接分发的短音频与 `manifest.toml`；长录音及制作中间件不入库。清单记事件ID、唯一clip ID、文字、文件名、时长、素材来源与风格。
- 缺某事件文件时降级到该事件的effects片段，仍缺则静默并记录一次告警；缺完整音频包时停用音频并显示状态。试听与素材校验阶段严格报出缺项。

## 7. 配置草案

下面仅为将来开发后的配置格式，当前配置解析器尚未支持，不直接写入运行中的 `config*.toml`。

```toml
[audio]
enabled = false                    # 功能交付并完成试听后，部署配置显式开启
backend = "pygame"                 # pygame | null
pack_root = "audio"                # 相对配置文件目录解析
style = "friends"                  # friends | clean
mode = "balanced"                  # balanced | key_only | effects_only
muted = false
volume = 0.6                       # 0.0~1.0
device_name = ""                   # 空值使用系统默认输出
allow_web_control = true
streak_thresholds = [3, 5, 7]
shutdown_min_streak = 3
comeback_deficit = 5
dominant_margin = 10
icebreaker_min_opponent = 5
banter_points_min = 3
banter_points_max = 5
min_voice_interval_seconds = 6.0
trigger_delay_seconds = 0.4
pending_ttl_seconds = 2.0
win_ttl_seconds = 5.0
repeat_guard_seconds = 30.0
preempt_fade_ms = 80
point_sound = true
history_limit = 512
```

开发时校验类型、有限数值、枚举、音量范围、正整数阈值、递增连击档位、插话最小值不大于最大值、有效期大于触发延迟、历史上限。首版连击档位限定为音效包已支持的3／5／7，缺映射明确报错，避免出现无法配音的配置。运行时音量等状态单独保存，不修改冻结的Config对象。

## 8. 网页、CLI与硬件接线

网页增加紧凑音频控制区：静音、音量滑块、频率模式、friends／clean风格、试听按钮，以及“正常／关闭／无设备／素材缺失”状态和最近播报文字。

- 计划 `POST /api/audio/settings` 接收允许的设置；`POST /api/audio/test` 按白名单事件试听。音频播放在运行AcePoint的电脑／树莓派，不在每个浏览器里播放，避免多台手机合唱。
- 设置接口受独立 `audio.allow_web_control` 开关控制；只接收类型正确的白名单参数，不接收文件路径或任意文本。请求进入引擎控制队列，返回202表示已接收；SSE回报实际生效状态。
- 试听限速且默认仅0:0时可用，进入真实计分立即取消试听；试听不计入比赛统计和已播记录。静音时不强制发声。
- 网页改变仅本进程有效；重启读取TOML。不新增云端账户或远程访问功能。
- 计划CLI：`acepoint --audio-test -c config.pi.toml`（独立音频试听，不加载摄像头或模型）；`acepoint --check` 在启用音频时额外检查依赖、设备及清单，检查默认不出声。
- 硬件先使用树莓派4的3.5mm输出接小型有源音箱；音箱型号和采购费用另选。系统输出路由、服务用户权限、音箱固定及供电需要实机验证。
- 增加音箱后重新实测整机功耗和续航，原BOM续航估算不能直接沿用。Pi配置目前默认只有LED／console；需要手机调音时再开启web后端，并使用可信本地网络访问。

## 9. 文件拆分与开发顺序

| 阶段 | 计划文件／修改点 | 可验收成果 |
|---|---|---|
| 1. 播放可行性 | `audio/player.py`，可选依赖audio，CLI音频测试 | Windows和Pi均能独立播放、静音、切设备；无设备不影响主程序 |
| 2. 得分事件与统计 | `state.py`、`engine.py`、`audio/events.py`、`audio/history.py` | 手势／手动统一接入，减分回算，结构化事件只处理一次 |
| 3. 规则与调度 | `audio/policy.py`、`audio/service.py`、`config.py` | 所有触发规则、优先级、取消、限流、去重通过自动化测试 |
| 4. 音频包 | `audio/manifest.py`、项目根目录`audio/`、`scripts/check_audio_pack.py` | 完整事件映射、可替换录音、时长／格式／路径校验和逐条试听 |
| 5. 网页接入 | `displays/__init__.py`、`displays/web.py`、模板、Telemetry | 手机可调音，SSE重连不重播，提供界面截图 |
| 6. 实机验收 | `config*.toml`、`deploy/README.md`、需求文档、回归测试 | 连续打满模拟局和球馆试用，记录效果、负载及续航 |

每个阶段可以先用NullPlayer／自制短测试音验证。最终“可交付”必须包含实际可听的音频包，不能只有事件日志和空目录。

建议先完成核心三／五／七连、终结、20平、29平、获胜的端到端链路，再在同一首版补全追平／反超／破蛋／普通插话和网页控制，避免同时调规则、音色与声卡。

## 10. 验收与回归

自动化使用假时钟、固定随机种子及NullPlayer，不用真实sleep等待或依赖声卡。

| 测试场景 | 必须满足的结果 |
|---|---|
| 左方连续拿1～8分 | 仅3／5／7生成对应连击候选，第8分无升级连击 |
